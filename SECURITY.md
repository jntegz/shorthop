# Security

## Reporting a vulnerability

Please report security issues privately through GitHub: **Security → Report a vulnerability** on this repository. Don't open a public issue. Include the steps to reproduce and the version (commit) you tested. Reporters are credited unless they prefer otherwise.

Shorthop is a personal project without a bug bounty.

## How Shorthop protects itself

- **Admin (`/_admin`):** by default, Cloudflare Access plus a password. The Worker verifies the Access JWT itself (issuer, audience, RS256 signature) on every request, so a misconfigured Access application or a direct request can't bypass it. Only owners (`ADMIN_EMAIL`) and people added in the admin get in. The password session is bound to the identity it was issued to.
- **People and permissions:** every API route has a permission rule, checked in the Worker after sign-in. A route without one is refused, and a test fails until it has one. Owners use the admin password. Everyone else chooses their own (PBKDF2, at least 12 characters) from a one-time invite link, which is stored only as a SHA-256 hash and works for 24 hours, once, for one Access email. Each person has their own session epoch, so a reset, a pause or a removal ends their sessions at once. Without Access there is only the owner. Someone with no permission at all can sign in but reads no links, and where a password-protected link goes, and its notes, take the Edit links permission. That covers destination checks and webhooks too: without it, the delivery log hides those destinations, and a webhook whose address was set or changed without it isn't sent them until someone with Edit links saves it. Webhooks set up by someone with Edit links keep receiving them. Adding a tag that feeds a shared report takes the permissions that report shows: See statistics, and See revenue for one with revenue.
- **Password resets:** a reset link goes only to the person's Access address, never to a typed one, and is stored as a SHA-256 hash. It works once, for 1 hour, and asking for one doesn't change the current password. Requests are limited per person (one per 15 minutes, 3 a day), per network (5 an hour) and in all (20 an hour), and wrong links lock the network like wrong passwords. Owners reset theirs through the Worker secret. Without Access there's no self-service reset.
- **Optional bot check:** Cloudflare Turnstile on the login and forgot-password pages, verified in the Worker with `TURNSTILE_SECRET`. Invite and reset links don't load it: their address is the secret, and it stays away from third-party scripts. It turns on only after a test passes. If Cloudflare can't be reached, logins still work, and the lockouts still apply.
- **Fail closed:** missing or malformed configuration keeps the admin shut. Access is only turned off by the exact value `ADMIN_AUTH="password"`; empty Access settings without it, or any other value, return an error.
- **Password login:** PBKDF2-SHA256 (25,000 or 100,000 iterations), constant-time comparison, a signed `__Host-` cookie with `SameSite=Strict`, CSRF and same-origin checks on every state change (requests with neither `Origin` nor `Sec-Fetch-Site` aren't from a browser and only need a session), 5 attempts per network before a lockout that doubles up to 24 hours, and a global pause after 30 failures in an hour from 5 or more networks, which a network that signed in to that account in the last 30 days skips (it keeps its own limit; only a keyed hash of the network is kept). Logging out revokes that session on the server, and a password change ends every session. Wrong API keys or tokens lock the sending network after 10 a minute, before anything is even compared; a request with no token at all isn't counted. On Workers Free at most about 5,000 wrong ones a day are recorded, so addresses that keep changing can't spend the database's daily writes; past that they're still refused, and locks already set still hold. API lockouts double only up to an hour (logins: a day), because the network is often an office or a home shared by several people and devices, and one script with a stale key mustn't shut the others out of the API for a day. Give each device and script its own personal key, so one can be revoked without touching the rest. IP addresses are never stored: lockouts and the login log use a keyed hash of the network.
- **API (`/api`):** personal API keys (`shp_…`, 256 random bits), stored only as a SHA-256 hash and shown once. A key does what was ticked on it, limited to what its owner may do at the moment it's used, and it stops working when it expires, is revoked, or its owner is removed, paused, waiting on a new invite link after a password reset, or (with Access off) isn't the owner. Webhooks a key set up keep running when it's revoked, and are flagged in Settings and System status until someone reviews them. Keys and the API token can't manage people, keys or sessions, can't remove a domain, can't see which email secrets are set, and can't change the email setup. In System status they get every check's state, but details only for whether the service is running, and no error text. The older `API_TOKEN` secret is compared in constant time. By default it can read links, statistics and destination checks (a fixed list of routes) and create links: changing or deleting links, overwriting imports, changing settings and reading webhooks, shared-statistics addresses, payment connections or customer data need the admin or a key, so a token lost with a phone can't retarget links people already have or collect anything that grants more access. It doesn't see where password-protected links go. `API_TOKEN_SCOPE="full"` lifts all of that.
- **AI assistants (MCP):** each tool reaches only its own route, a key sees only the tools its permissions allow, and `fetch_preview` is marked as reaching the open web, drops query strings and returns short fields. Results holding text other people wrote are labelled as untrusted, but a label doesn't stop a model from following what it says. What limits the damage is the key: give an assistant only the permissions it needs, and use your client's approval prompts for changes.
- **Secrets** are Wrangler secrets. The setup passes them to Wrangler through stdin and never writes them to disk; the admin never displays them, and System status reports only whether they're set and long enough.
- **Deploy to Cloudflare installs:**
  - The owners' password is the plain `ADMIN_PASSWORD` secret, compared in constant time and ignored below 9 characters. A hash (`ADMIN_PASSWORD_HASH`) wins once it's set.
  - The session secret and the visitor salt are generated once and kept in D1 until you set them as secrets. Anyone who can read your D1 database can then read them; that's someone who already has access to your Cloudflare account. They're never in a backup.
  - Until you add an `ENCRYPTION_KEY` secret, the secrets stored in D1 (webhook, share and payment ones) are encrypted with that generated session secret, in the same database. System status warns about it until you do; the daily cleanup then re-encrypts them, and nothing stops working.
- **Outbound requests:**
  - Destination checks, the social-preview fetch and webhooks only reach public addresses: private, loopback, link-local and reserved ranges (the documentation and benchmarking ones included) are refused. Each redirect is checked again before it's followed, or isn't followed at all (webhooks).
  - This looks at the address as written. A public name that resolves to a private address isn't caught here: stopping that is left to Cloudflare's network, and whether it always does hasn't been verified.
  - Requests to hostnames in the Worker's own zone go through Cloudflare like a visitor's (`global_fetch_strictly_public`), so your Access and WAF rules apply to them. The social-preview fetch never reads Shorthop's own short links, and is rate-limited per person.
  - `link.clicked` webhooks go out for at most 120 clicks a minute from one network, counted at each Cloudflare location. Further clicks from that network that minute send none.
  - Email provider hosts are fixed in the code, redirects are refused, and the recipient comes only from configuration.
  - Webhooks are signed with HMAC-SHA256 (`X-Shorthop-Signature`). Their secrets are encrypted at rest with AES-GCM, with a key derived from `SESSION_SECRET`, and shown only once.
- **Password-protected links and shared statistics:** PBKDF2 at 30,000 iterations on Workers Free (a check fits its CPU limit) and 100,000 on Paid (`WORKERS_PLAN`). Ten wrong passwords in an hour lock out the network that sent them, for a minute at first and up to 15 minutes. After 20 wrong passwords for one link in an hour, from any networks, every network that guessed wrong waits up to 15 minutes, and all other networks together get at most 20 tries an hour while it is on, so guesses spread over many networks (an IPv6 /48 holds 65,536 of them) stay bounded. A visitor who types the right password on the first try still gets in, so one person guessing can't lock everyone else out. Someone guessing from more than 20 networks can use up those tries; then a visitor with the right password also waits until the brake runs out (a minute at first, up to 15). A correct password is remembered for 12 hours in a cookie scoped to that link and signed with `SESSION_SECRET`; changing the link's password ends every remembered access. The destination is never revealed before the password, not even to preview crawlers.
- **Link edits:** an edit changes only the fields it sets, so two people editing a link don't undo each other, and API clients can send the link's `version` to get a 409 instead of overwriting a newer state. Restoring an old version leaves the password as it is now unless you ask for the version's.
- **Destinations:** a link target, an import row, a bio button and a routing variant follow the same rules: `https://`, no username or password, not your own short domains. A `HEAD` request on a link flagged as unsafe gets the warning's status and no address. With **Pass query parameters through** on, whoever opens a link can add parameters that reach the destination. A parameter the destination already has keeps its value, but the destination shouldn't trust the others.
- **Turning a link off isn't instant.** Redirects read a copy cached at Cloudflare's edge for `KV_CACHE_TTL` seconds (60 by default, 30 at the lowest), and a change also takes time to spread, so a disabled or newly protected link can still work for a minute or two. For an emergency, change the destination at its source too.
- **Logs:** the Worker's own log lines contain no addresses with secrets in them, and Cloudflare's per-request invocation logs and traces are turned off in the config (2.0.3). A `wrangler.jsonc` from before that gets this from `npm run setup -- upgrade`, and `npm run deploy` refuses it until then. Rate limiters get a keyed hash of the network, not its address.
- **Updates (Deploy to Cloudflare copies):** the Update Shorthop workflow from 2.0.3 doesn't run the release's code. A read-only job checks the release, and refuses one older than yours unless you ask. The job that can write treats the release as files and runs the updater already in your copy, without install scripts; a copy from before 1.2.0 has none, and uses the 2.0.2 updater, fixed by commit in the workflow. **This protects you only once that workflow file is in your copy.** A workflow can't replace itself, and an update doesn't change it, so a copy that hasn't pasted it in keeps the old one, which installs and runs the release's code in a job that can write to your repository. Paste it in before you update ([how](docs/SETUP.md#update-button)). Releases aren't signed: the workflow trusts that a tag on the upstream `main` branch is what the maintainer published.
- **Admin pages** are served with a strict Content Security Policy, `X-Frame-Options: DENY` and `no-store` caching. Every page and redirect sends `Strict-Transport-Security`.
- **Visitors:** no IP addresses are stored, and no cookies are set except on a password-protected link. The daily visitor hash uses a random salt per day that's deleted once the day is over. See [docs/PRIVACY.md](docs/PRIVACY.md).
- **Website analytics:** anyone can send the tracker's events, so a name or email a page sends with `identify` is marked unconfirmed in the admin; only `POST /api/sites/:id/identify` from your server counts as verified. A checkout reference sent by a page counts only for a payment made in the 24 hours before it (or the hour after), or begun then by the provider's own signed date (a bank debit settles days after its checkout). It is a low-confidence match and never says who the buyer is. Neither does a reference on a checkout address (`sh_ref` and the like), which anyone can set, even when a signed provider webhook repeats it: it credits the visit, copies no email and doesn't extend a privacy request. Only an email your server reported, or a visitor your server named for the payment, does. References stored before 2.0.3 don't say where they came from, so they are treated like a page's, except that one naming a subscription still counts for that subscription's payments, at low confidence, until it expires after 90 days: otherwise a trial begun before the upgrade would lose its source. With Global Privacy Control or Do Not Track the server ignores a browser's `identify` and keeps no checkout reference for it. An erased browser ID is refused from then on, and a keyed-hash ledger lets you erase people again after restoring a backup (docs/PRIVACY.md). A short-link click token counts on the site it was made for, for at most three visitors in ten minutes (per Worker instance), and only exactly as it was issued. The tracker's checkout events are public as well: a faked one can take a timing match for its own visit, or, with several, keep a payment from matching by timing at all. These signals are public: revenue by source that rests on them is an estimate, marked low confidence. The revenue totals themselves come from the providers' events.
- **Payments:** webhooks are verified per provider. Gumroad doesn't sign its pings, so its webhook address carries a random token. With an access token, each sale is read back from Gumroad and stored as Gumroad reports it, and refunds, disputes and cancellations count as confirmed only when Gumroad's answer says so; a ping for a sale Gumroad says doesn't exist is refused. If Gumroad can't be asked, doesn't show the event yet, or its answer doesn't mention it, the event is kept and labelled unverified rather than lost, and a later delivery or import that can confirm it replaces it with Gumroad's values. An unverified refund or dispute of a confirmed sale, or of no known sale, is listed but counts as 0 in revenue until then. An unconfirmed cancellation leaves the subscription as it was and shows in System status. Without a token, payments and refunds are labelled unverified and refunds count against their equally unverified sale, up to its amount, and cancellations are applied. So anyone with the webhook address can add an unverified sale while Gumroad's API is unavailable, and can always do so without a token. Payment ids are global, so a payment belongs to one site. When sites share a provider account, a product filter decides for a payment that names products, a charge's visit reference decides for the site that visit belongs to, and a refund or dispute follows the site that has its charge. A row another site stored first moves only if that site's own copy agrees: the same amount and currency, and the same visit reference, or for a refund the same charge. It moves without the email and customer ID stored with it. Otherwise the first site's webhook keeps it and the other's write is refused and counted in System status, as is a subscription id that already belongs to another site. Refunds above their charge are capped at it and flagged, whichever arrives first; ones in another currency, or with no charge found, are flagged and kept.
- **Redirect targets** must be `https://` and can't point back at the shortener's own hosts.

## Workers Free: protect the daily request cap

On Workers Free, the 100,000 requests a day are a hard cap for the whole account, and every request to a short domain counts, including requests for slugs that don't exist. Once the cap is used up, Cloudflare answers with error 1027 until midnight UTC: every short link stops working. The Worker can't prevent that, because each request that reaches it already counts.

So anyone who sends enough requests can take your links down for the rest of the day. Two things help:

- **A rate-limiting rule** in each short domain's zone stops a single client from doing it quickly. Blocked requests stop at Cloudflare's edge and never reach the Worker. In the Cloudflare dashboard, for the zone:
  1. **Security → WAF → Rate limiting rules → Create rule.**
  2. **If incoming requests match:** URI Path wildcard `/*`. The Free plan can't match on the hostname, so the rule covers every site in the zone; mind that if the zone serves more than Shorthop.
  3. **With the same characteristics:** IP.
  4. **When rate exceeds:** 50 requests per 10 seconds. A visitor sends one request per click; opening the admin loads a few dozen files, so raise the limit if the admin is on this zone and you hit it.
  5. **Then take action:** Block, for 10 seconds.
  6. Deploy.

  The Free plan allows one rule per zone. If the admin login is on the same zone, this rule takes the place of the login rule below; Shorthop's own lockout still limits password guesses. A rule raises the bar but doesn't remove it: many clients, or one that stays under the limit for hours, can still use up the day.
- **Turn off the `workers.dev` address** once your short domain works: set `workers_dev = false` in your Wrangler config. The rule above protects your zone, and the `workers.dev` address isn't part of it.
- **Workers Paid** ($5/month) has no daily cap: requests beyond the 10 million a month included are billed instead. Choose it if your links must not go down.

The database has a daily allowance on Free too: 100,000 rows written. Website events come from anyone's browser, so on Free they may write at most 60,000 rows a day, counted as D1 reports them. A visit writes about five rows for its first event and about three for each later one, so a typical visit takes about eleven and the budget covers about 5,000 to 6,000 of them. Past that, events are accepted but not stored until 00:00 UTC; System status warns at 80% and again when the day's budget is used up. The rest of the allowance stays for logins, links and payments. Failed sign-ins are bounded too: a network that is locked out, or held back by a link's brake, writes nothing more, and wrong API keys have their own daily limit.

## Password-only mode: add a rate-limiting rule

With `ADMIN_AUTH="password"` the login page is reachable by anyone. Shorthop's own lockout slows guessing, but stopping floods at Cloudflare's edge is cheaper and keeps the noise out of your logs. In the Cloudflare dashboard, for the admin host's zone:

1. **Security → WAF → Rate limiting rules → Create rule.**
2. **If incoming requests match:** URI Path equals `/_admin/login`. (The Free plan matches on the path only; on higher plans you can add `http.request.method eq "POST"` so that only attempts count.)
3. **With the same characteristics:** IP.
4. **When rate exceeds:** 10 requests per 10 seconds (the Free plan allows one rule with a 10-second period).
5. **Then take action:** Block, for 10 seconds (longer on paid plans).
6. Deploy.

Better still, keep Cloudflare Access on: `npm run setup -- access`.

**A known trade-off:** after 30 failed logins in an hour from 5 or more networks, Shorthop pauses logins for 15 minutes. A network that signed in to the account in the last 30 days is let through the pause (its own lockout still applies), and existing sessions keep working. Without Access, an attacker with that many networks can still keep you out from a network you haven't used yet, and nothing on the login page can tell you from them. Then wait for the pause to end, sign in from a known network, or lift the pause from your Cloudflare account, which needs no admin login: `npx wrangler d1 execute DB --remote --command "DELETE FROM auth_failures WHERE key IN ('*', '*people')"` (the same `DELETE` works in the dashboard's D1 console). Changing the admin password doesn't lift it. An attacker who keeps failing can start it again, so if this repeats, put Access in front: it removes the problem, because the login page is then unreachable without your email.

## Hardening checklist

- Use the generated admin password and keep it in a password manager.
- Turn on **Always Use HTTPS** for each zone. Shorthop also sends `Strict-Transport-Security`, so a browser that has visited once stays on HTTPS.
- Give each script or device its own personal API key with only the permissions it needs, and an expiry where that fits. Revoke the key if the device (such as a phone with the iOS Shortcut) is lost.
- If you still have the older `API_TOKEN`, move to keys and delete it (`npx wrangler secret delete API_TOKEN`). Until then, keep `API_TOKEN_SCOPE` at `create`.
- Turn on Cloudflare Access, even on a Deploy to Cloudflare install: password-only sign-in leaves the login page open to anyone. Without it, use a long random password; System status warns about a plain `ADMIN_PASSWORD` under 16 characters.
- Once your own domain works, set `workers_dev = false`, or `WORKERS_DEV_ADMIN = "off"` to keep the workers.dev address for links only: Cloudflare rules on your zone don't cover it. With no short domain yet, it stays available, since it's the only way in.
- When someone leaves, remove them in Settings → People and take them out of the Access policy.
- On Workers Free, add the rate-limiting rule from [the daily cap section](#daily-cap).
- Monitor a real short link from outside: an uptime service that requests one of your links and expects a `302` notices a used-up daily cap or a broken deploy within minutes. `/health` only shows that the Worker runs; it doesn't read the link store.
- Review **Settings → Access & security** for failed logins now and then; the System status page emails you when a check fails.
